title: One file per decision, in docs/decisions
status: decided
area: docs
---

## What

A new decision, and a failure that could recur, is one Markdown file in
`medbrains/docs/decisions/`, named `YYYY-MM-DD-short-slug.md`, with a fixed front section
(date, title, status, area) and three headings: What, Why, Rejected.
`medbrains/scripts/check_decisions.py` checks the name and the shape in CI (the job
"Decision files are well formed").

`medbrains/docs/DECISIONS.md` is the history up to today and takes no new rows. A pull request
opened before this moves its row with `medbrains/scripts/decision_row_to_file.py`; until the
open ones have, a row added there is a warning, not a failure.

The index (`decisions/README.md`) is generated by `make decisions-index` and is not
committed. The file names sort by date, so the folder listing is already in order.

## Why

Every pull request appended a row to the end of the same file, so every merge put every other
open pull request into conflict on GitHub. `.gitattributes` has had `merge=union` for that file
since #5295, but GitHub's own merge ignores it: on 2026-11-22, six pull requests GitHub marked
as conflicting (#6198, #6199, #6201, #6202, #6204, #6208) merged cleanly with local git. Each
conflict meant merging the base in by hand and a full new CI run, and a conflicting pull request
cannot enter a merge queue at all.

Two pull requests that each add a file touch no common line.

## Rejected

- Keeping the one file and relying on `merge=union`: GitHub does not apply it.
- A committed index: it would be the one file every pull request edits, which is the problem
  being removed.
- Regenerating a committed index on each push to the release branch: a bot commit to a
  protected branch on every merge, to save a folder listing nobody needs sorted twice.
- Converting the rows of open pull requests here: each author's row is in their branch, not in
  this one.
- A changelog-fragment tool (towncrier and the like): a new dependency for what a folder and a
  40-line check do.
