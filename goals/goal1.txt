# MedBrains Goal 1 - Patient Continuity Problem Statement

## Problem Statement

MedBrains must stop behaving like separate hospital modules that only sit next to
each other. The product problem is broken patient continuity.

A patient can be registered, sent to OPD, moved to emergency, admitted into IPD,
screened in a camp, prescribed medicines, billed, shown on a token board, opened on a
mobile device, or displayed on TV/kiosk screens without every surface carrying the
same patient context. Staff then have to manually reconnect the patient, encounter,
admission, order, invoice, queue, permission, masking, and event state.

That broken continuity creates the real hospital pain:

- front desk users re-search patients and repeat registration context;
- OPD, emergency, and IPD users lose the current clinical or operational event;
- pharmacy and billing users reconstruct work from partial patient information;
- administrators cannot see which actions, reports, settings, and devices are
  actually governed by the same workflow;
- public displays and edge devices risk showing stale or excessive patient data.

The result is slower care, billing leakage, privacy exposure, patient-safety risk,
weak regulatory traceability, and poor adoption even when each module exists.

## Desired Outcome

One patient journey should remain coherent from registration through OPD, IPD,
emergency, camp, pharmacy, billing, reports, and web/mobile/TV/kiosk/token-board
surfaces.

Wherever a user enters the journey, the system should preserve the active context:

- who the patient is;
- which encounter, admission, camp, queue, order, prescription, invoice, or discharge
  event is active;
- which actions are available now;
- why an action is unavailable;
- what information this user is allowed to see or edit;
- how the same state appears in reports, settings, token boards, printouts, mobile,
  TV, and kiosk surfaces.
- how every visible label, helper text, validation message, and error message is
  delivered through i18n so multilingual hospital teams do not get hardcoded
  workflow copy.

## User Pain To Remove

Front desk staff should register or identify a patient once and immediately see the
correct next care handoff without overexposing demographic details.

Doctors and nurses should open the right patient from the right queue, understand the
current OPD, emergency, camp, or IPD state, and act without guessing which record the
system will use.

Ward staff should manage an IPD admission through durable routes and tabs that keep
bed state, orders, pharmacy handoffs, billing readiness, discharge readiness, reports,
and role-based actions tied to the same admission.

Pharmacy staff should dispense or return medicines from real patient-linked orders
with formulary, schedule, controlled-substance, batch, expiry, FEFO, allergy, and
order status context visible at the point of work.

Billing staff should create invoices, payments, payer claims, and discharge bills
from actual patient events, admissions, orders, and pharmacy activity, not from
manual reconstruction.

Administrators should be able to find patient-journey gaps in settings and reports:
missing event backing, missing permissions, unsafe masking, missing report coverage,
or device surfaces that are not using the same source of truth.

Hospital teams should be able to localize labels, form guidance, blocking reasons,
validation feedback, and error messages without code edits, because language support
is part of usable clinical workflow, not a later cosmetic layer.

Patients and public viewers should see only the minimum safe information on token
boards, kiosks, printouts, mobile screens, and TV displays while those surfaces still
reflect the same live workflow as the staff app.

## Success Statement

This goal is achieved when a hospital user can follow a patient from registration to
care delivery, dispensing, billing, reporting, and device display without unnecessary
re-searching, duplicated entry, ambiguous actions, unsafe identity exposure,
unexplained blocking, or disconnected reports.

## Working Decision Filter

Each product slice starts with one concrete patient-continuity break:

- which patient context is getting lost;
- which hospital role feels that loss;
- which workflow, event, permission, masking, report, setting, or device surface is
  responsible;
- what evidence will show the break is fixed.

The goal is not to add general HMS rules. The goal is to remove named breaks that
make real patient work slower, less safe, less traceable, or harder to adopt.
