# MedBrains Goal 1 - Problem Statement

## Problem
MedBrains is not yet fully usable as an end-to-end hospital workflow system because the
core patient journey is still too loosely connected across modules. Users can register
a patient, open OPD/IPD/emergency/camp/pharmacy/billing screens, and see some actions,
but the application does not yet behave like one tightly integrated operational system.

The main problem is not lack of screens. The problem is that patient context, event
state, permissions, masking, settings, token boards, and reports are not consistently
linked across the real workflows hospital staff perform every day.

## Affected Workflows
The priority workflow chain is:

Patient registration -> OPD -> IPD -> Emergency -> Camp -> Pharmacy -> Billing ->
Reports / Settings / Configuration

Mobile, TV, and kiosk surfaces must support the same operational chain where they are
part of the workflow, especially token systems, queue boards, check-in, bedside views,
and edge-device dashboards.

## User-Visible Symptoms
- Staff must re-search or re-select the same patient when moving between modules.
- OPD, IPD, emergency, camp, pharmacy, and billing feel like separate pages instead of
  linked patient-care workspaces.
- Some important workflows are hidden in drawers even though they should be durable
  routes or tabs that can be reopened, audited, shared, and deep-linked.
- Patient context is not always visible when the user is inside clinical or financial
  workspaces.
- IPD does not yet consistently use the top patient context, left navigation rail, and
  right contextual actions for ward-style work.
- Actions are not always activated by real domain state. Buttons can appear without a
  clear event reason, or disabled actions do not always explain what event or permission
  is missing.
- Permission and masking coverage exists in pieces, but Settings must expose the full
  matrix for screens, tabs, tables, columns, input boxes, actions, widgets, printables,
  and device surfaces.
- Field masking is not yet consistently applied everywhere a sensitive table value,
  patient identity, phone, clinical note, regulatory field, or financial value appears.
- Reports and indicators are not yet tightly fed by the same workflow events that drive
  operational screens.
- Mobile, TV, and kiosk flows need clearer alignment with web routes, token boards,
  privacy rules, performance constraints, and edge-device stability.

## Required Product Outcome
MedBrains should behave like an enterprise hospital command workspace:

- A user starts from a patient or module queue and can move through the next valid
  workflow step without losing context.
- Durable workspaces use routes; stable sections inside workspaces use tabs; drawers
  and modals are limited to short transient tasks.
- OPD, IPD, emergency, camp, pharmacy, and billing actions are driven by patient state,
  domain events, and permission decisions.
- Every action that is hidden, disabled, masked, printable, or edge-device-visible has
  a clear reason in the access/event matrix.
- Settings provides the administrative source of truth for permission coverage,
  masking coverage, route coverage, print/device coverage, and workflow readiness.
- Patient-sensitive and financial data is masked or hidden consistently across web,
  mobile, TV, kiosk, tables, cards, forms, print outputs, dashboards, and reports.
- Token dashboards are available and governed across web, mobile, TV, and kiosk
  surfaces, with public displays showing only safe token-level information.
- Reports and indicators reflect actual workflow events rather than isolated page state.

## Priority Problem Slices
1. Patient context continuity
   Registration, OPD, IPD, emergency, camp, pharmacy, and billing must carry patient
   context through routes, tabs, action panels, and handoff controls.

2. Event-driven action readiness
   Each module action must map to the event or state that makes it valid, plus the
   permission that allows it. Disabled actions should explain the missing event,
   context, or permission.

3. Settings access matrix
   Settings must enumerate all governed surfaces: screens, tabs, tables, columns,
   input boxes, actions, widgets, printables, token boards, TV, mobile, and kiosk
   targets. It must show gaps instead of leaving loose screens or fields invisible.

4. Field masking consistency
   Shared masking behavior must be used for patient identity, clinical, regulatory,
   operational, and financial fields wherever they appear.

5. IPD command workspace
   IPD should use a top patient context strip, left rail, central tabbed workspace, and
   right contextual action/readiness panel so ward work is not scattered into drawers.

6. Token and edge-device integration
   Token boards, queue boards, kiosk check-in, mobile staff views, and TV displays must
   share route/device metadata, privacy rules, and event-fed read models.

7. Reports and indicators
   Reports should be linked to workflow events and show operational, clinical, billing,
   pharmacy, NABH, and configuration readiness indicators.

## Success Criteria
The goal is not complete until current code and runtime behavior prove all of the
following:

- A patient can move through registration, OPD, IPD or emergency, camp where relevant,
  pharmacy, billing, and reports without losing context or re-searching unnecessarily.
- Each core module has route-based durable workspaces and uses tabs or panels for stable
  subviews instead of burying full workflows in drawers.
- Critical actions are event- and permission-gated, with visible disabled reasons where
  showing the unavailable action helps the user understand the next step.
- Settings shows the full permission/masking matrix for screens, tabs, tables, columns,
  inputs, buttons/actions, widgets, printables, and platform/device targets.
- Sensitive data masking is enforced consistently through shared utilities/components
  and is reflected in web, mobile, TV, kiosk, print, and report surfaces.
- Token dashboards work across web, mobile, TV, and kiosk with public-display privacy.
- Reports and indicators are fed by the same workflow state and events used by the
  operational modules.
- Static checks, relevant unit tests, and focused UI/runtime checks pass for the touched
  areas.

## How To Use This Goal
Use this file to choose implementation slices by problem impact. Each slice should
answer:

1. Which user-visible workflow problem does this fix?
2. Which modules or surfaces become more tightly linked?
3. Which event, permission, masking, route, setting, report, mobile, TV, or kiosk gap is
   closed?
4. What evidence proves the slice works?

Avoid treating this goal as a generic rules list. The work should make the stated
patient-flow usability problem measurably less true.
