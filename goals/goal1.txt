# MedBrains Goal 1 - Problem Statement

## Problem Statement

MedBrains is not yet usable as a continuous hospital operations workspace because the
core patient journey is fragmented across loosely connected modules. The application
has many screens, but registration, OPD, IPD, emergency, camp, pharmacy, billing,
settings, reports, mobile, TV, and kiosk surfaces do not yet behave like one
event-aware system centered on the patient.

Hospital staff should not have to remember which page to open next, re-search the same
patient, infer why an action is unavailable, or guess whether a field is governed by a
permission, masking rule, regulatory rule, report indicator, or device-display policy.
The system must make the next valid workflow step visible from the current patient,
module state, event history, and permission context.

## Why This Matters

This is a product usability and operational safety problem, not just a navigation
problem. In a hospital, broken context between modules causes repeated work, missed
handoffs, inconsistent privacy behavior, weak auditability, poor public-display
controls, and reports that do not reflect the same events staff use to run the floor.

The current risk is that MedBrains can look feature-rich while still feeling incomplete
in day-to-day use because each module works more like a separate page than part of a
single clinical and administrative workflow.

## Affected Patient Journey

The priority journey is:

Patient registration -> OPD -> IPD or emergency -> camp where relevant -> pharmacy ->
billing -> reports and indicators.

Settings and configuration must support this journey by exposing the permission,
masking, route, action, report, token, print, mobile, TV, and kiosk governance behind
it. Edge surfaces such as kiosks, token dashboards, staff mobile screens, bedside
views, and public TV boards must follow the same workflow state and privacy rules as
the web application.

## Observable Symptoms

- Patient context is lost or hidden when moving between registration, OPD, IPD,
  emergency, camp, pharmacy, and billing.
- Full workflows are sometimes buried in drawers instead of durable routes or stable
  tabs that can be reopened, linked, audited, and tested.
- OPD, IPD, emergency, camp, pharmacy, and billing actions are not consistently enabled
  by real domain events or explained when unavailable.
- IPD does not yet consistently feel like a ward command workspace with patient
  context, navigation, task readiness, and contextual actions visible together.
- Permission coverage exists in pieces, but Settings does not yet prove every screen,
  tab, table, column, input, action, widget, printable, report, token board, mobile
  view, TV view, and kiosk flow is governed.
- Masking rules are not yet consistently applied to sensitive patient identity,
  contact, clinical, regulatory, operational, and financial data everywhere the data
  appears.
- Reports and indicators are not yet fully sourced from the same workflow events that
  activate operational screens and actions.
- Mobile, TV, and kiosk experiences are not yet clearly tied to the same routes,
  tokens, privacy rules, event state, and readiness model as web.

## Target Outcome

MedBrains should behave like an enterprise hospital command workspace:

- Patient context remains visible and actionable across registration, OPD, IPD,
  emergency, camp, pharmacy, billing, reports, and settings.
- Durable clinical and operational work happens in routes and tabs; drawers and modals
  are limited to short transient tasks.
- Menus, tabs, buttons, table actions, print actions, token displays, and device
  surfaces activate from domain events, current patient state, and permissions.
- Disabled or hidden actions have a traceable reason: missing event, missing patient
  context, missing permission, masking rule, configuration gap, or regulatory block.
- Settings is the administrative source of truth for access, masking, route, report,
  print, token, mobile, TV, and kiosk coverage.
- Reports and indicators are fed by the same event model used by operational modules.
- Public and edge-device surfaces expose only the minimum safe information required for
  their workflow.

## Problem Slices To Close

1. Patient context continuity across registration, OPD, IPD, emergency, camp,
   pharmacy, billing, reports, and settings.
2. Event-driven action readiness for module menus, tabs, buttons, handoffs, print
   actions, token boards, and reports.
3. Settings coverage for permissions, masking, routes, reports, widgets, printables,
   mobile, TV, kiosk, and token surfaces.
4. Shared masking behavior for identity, contact, clinical, regulatory, operational,
   and financial fields.
5. IPD command workspace with top patient context, left navigation, central tabs, and
   right-side readiness/actions.
6. Token and edge-device integration across web, mobile, TV, and kiosk.
7. Report and indicator linkage to canonical workflow events and payload fields.

## Completion Evidence

The goal is complete only when runtime behavior and checked code show that:

- A patient can move through the priority journey without unnecessary re-searching or
  context loss.
- Core modules expose durable workspaces with stable routes/tabs for real workflows.
- Critical actions are event-gated, permission-gated, and explain unavailable states
  where the unavailable action is shown.
- Settings displays coverage and gaps for governed UI, data, report, print, token, and
  device surfaces.
- Sensitive fields use shared masking policies consistently across web, mobile, TV,
  kiosk, print, reports, tables, cards, and forms.
- Token dashboards and public displays respect safe public-display data rules.
- Reports and indicators use the same canonical events and payload contracts as the
  operational workflow.
- Static checks, focused unit tests, and relevant UI/runtime checks pass for every
  touched area.
